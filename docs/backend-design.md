# 后端设计:日报提交服务 + 飞书多维表格

日期:2026-09-13
状态:设计草案,待确认见第 11 节

## 1. 目标

- 每台机器上的 App 只需配置**一个 API 地址 + 一个 API Key**,就能把当天的日报提交出去。
- 提交结果落到**飞书多维表格**,团队在那里查看、筛选、统计。
- 不把任何飞书应用密钥放进客户端。

## 2. 为什么必须有后端

飞书多维表格的写入接口需要 `tenant_access_token`,而它由**应用 App ID + App Secret** 换取。如果让客户端直接写表,只有两种可能:

1. 把 App Secret 打进安装包 → 任何人反编译即可读写整个表格,不可接受;
2. 每人自建一个飞书应用 → 3–10 人规模下管理成本高于收益。

因此:**凭据只留在服务端,客户端只持有一把可撤销的 API Key**。后端顺带承担了幂等、校验、审计与"重新生成后覆盖"这些客户端做不了的事。

## 3. 架构

```
┌────────────┐  HTTPS  POST /api/v1/digests          ┌────────────────────┐
│  App       │  Authorization: Bearer <member key>  │  提交服务(薄后端) │
│ (每台机器) │  Idempotency-Key                     │  ① 鉴权→成员身份   │
└────────────┘ ───────────────────────────────────▶ │  ② 校验            │
      ▲                                             │  ③ 幂等/覆盖       │
      │ 201 {record_ids}                            │  ④ 写多维表格      │
      └──────────────────────────────────────────── │  ⑤ 审计日志        │
                                                    └─────────┬──────────┘
                                                              │ tenant_access_token
                                                              ▼
                                                    ┌────────────────────┐
                                                    │ 飞书多维表格       │
                                                    │ (FIELDS 见第 6 节) │
                                                    └────────────────────┘
```

组件:

| 组件 | 作用 | 选型建议 |
| --- | --- | --- |
| 提交服务 | HTTP API + 鉴权 + 幂等 + 写表 | Python + FastAPI(与现有引擎同栈),单容器 |
| 元数据库 | API Key、提交记录、行映射 | SQLite(3–10 人足够)或 Postgres |
| 反向代理 | TLS、限流 | Caddy(自动证书)或平台自带 |
| 飞书自建应用 | 提供多维表格读写权限 | 已存在或新建,仅后端持有密钥 |

## 4. 接口契约

### 4.1 提交日报

```
POST /api/v1/digests
Authorization: Bearer <member-api-key>
Content-Type: application/json
Idempotency-Key: <member_id>:<date>:<content_sha256>
```

请求体(与现有引擎的 `submit()` 载荷兼容并扩展):

```json
{
  "date": "2026-09-13",
  "generated_at": "2026-09-13T18:02:08+08:00",
  "release_version": "v0.5.1",
  "report_chars": 832,
  "coverage_note": "当天入库 66 条(提示词 11 / 最终文本 53 / 交付物 2);送模型 62 条 / 14,662 字符",
  "work_items": [
    { "title": "报告窗口正文渲染修复", "desc": "…", "status": "completed",
      "source_task_ids": ["codex/01a0…", "deepseek-harness/…"] }
  ]
}
```

**注意:请求体里没有成员字段。** 成员身份一律由 API Key 推导(见 5.1),客户端传什么名字都不采信,避免冒名提交。

响应:

```
201 Created
{ "submission_id": "sub_01J…", "member": "张三", "date": "2026-09-13",
  "mode": "created", "records": [{"index": 0, "record_id": "rec…"}],
  "submitted_at": "2026-09-13T18:02:11+08:00" }
```

`mode` 取值 `created`(首次)/ `updated`(同一天内容变化后覆盖)/ `unchanged`(完全相同,幂等命中,返回原记录,HTTP 200)。

### 4.2 错误语义

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `invalid_json` | 请求体不是合法 JSON |
| 401 | `invalid_key` | Key 不存在或被禁用 |
| 403 | `member_disabled` | 成员被停用 |
| 409 | `date_locked` | 该日期已锁定(可选,见 9.3) |
| 422 | `validation_failed` | 字段缺失/超长/工作项为空 |
| 429 | `rate_limited` | 超过每 Key 限额(建议 10 次/分钟) |
| 502 | `bitable_unavailable` | 飞书写入失败(含 `code != 0`) |
| 503 | `not_ready` | 后端拿不到 tenant_access_token |

**关键约束**(与需求 FR-7.2/7.7 一致):只要表格没写成功,就必须返回非 2xx,客户端**绝不能标记为已上报**。飞书接口常在 HTTP 200 下返回 `code != 0`,必须解析响应体判断。

### 4.3 其它接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/me` | 用 Key 换取自己的成员信息,供客户端「设置」保存时校验 Key 是否正确 |
| `GET /api/v1/digests?date=YYYY-MM-DD` | 查询某天是否已提交(便于客户端显示"本周已提交 N 天") |
| `GET /healthz` | 存活 + 飞书 token 可用性 |
| `POST /admin/keys` | 管理员签发成员 Key(见 5.2),不对外暴露 |

## 5. 鉴权设计

### 5.1 API Key

- 一把 Key 绑定一个成员:`key_id`(公开前缀,便于日志与撤销)+ 随机 32 字节密钥。
- 展示格式:`dag_<key_id>_<secret>`,客户端只看到这一串。
- 服务端**只存 `sha256(secret)`**,不存明文;校验用恒定时间比较。
- 客户端保存在 `.env`(权限 `0600`),与现有 `DIGEST_FEISHU_WEBHOOK` 同级;设置界面只写不回显(沿用 FR-11.3 的口径)。
- 成员名、工号、启用状态都记在服务端,客户端不需要再填姓名(现有 `DIGEST_MEMBER` 仅作离线显示的兜底)。

### 5.2 签发与轮换

- 管理员用 `POST /admin/keys`(或一个 CLI)创建,返回**一次性明文 Key**;之后无法再查看。
- 轮换:签发新 Key → 成员在设置里替换 → 撤销旧 Key。撤销即时生效(服务端查表)。
- 首次部署需要一把"引导 Key"(环境变量注入)以便签发其余 Key,签完即撤。

## 6. 多维表格设计

### 6.1 主表:日报明细(一行一个工作项)

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 提交ID | 文本 | `{member_id}-{date}`,用于幂等与批量覆盖 |
| 日期 | 日期 | `date`,建议设为表格主字段的排序键 |
| 成员 | 文本(或"人员") | 由 Key 推导;若表格在同一个租户内,可用人员字段支持按人筛选 |
| 标题 | 文本 | 工作项标题 |
| 内容 | 多行文本 | 工作项正文 |
| 状态 | 单选 | `completed` / `in_progress` / `blocked` |
| 字数 | 数字 | 该项 title+desc 字数 |
| 来源 | 多选 | `codex` / `pi` / `deepseek-harness` |
| 提交时间 | 日期时间 | 服务端收到的时间 |
| 应用版本 | 文本 | `release_version`,便于排查旧版本 |

**为什么一行一个工作项**:可以直接按人 / 按日期 / 按状态 / 按来源筛选与聚合,仪表盘无需额外处理;缺点是行数较多(每人每天 3–20 行)。若更希望"一行一份日报",把 `标题/内容/状态` 合并成一个富文本字段即可,但筛选能力会下降。

### 6.2 可选副表:日报汇总(一行一人一天)

| 字段 | 类型 |
| --- | --- |
| 提交ID / 日期 / 成员 / 条数 / 总字数 / 提交时间 / 当天覆盖度说明 |

用于团队看板(谁交了/谁没交),由后端在同一次提交里一并写入。

### 6.3 飞书侧准备步骤

1. 开发者后台创建**自建应用**,开通 `bitable:app`(读写多维表格)。
2. 把应用添加为**目标多维表格的协作者**(或在文档「…」→ 添加文档应用),否则报权限错误。
3. 发布应用版本(权限变更需重新发布才生效)。
4. 记录 `app_token`(多维表格 URL 中 `/base/` 之后那段)与 `table_id`(`?table=` 参数),放进后端环境变量。

## 7. 服务端实现要点

- **token 缓存**:`tenant_access_token` 有效期约 2 小时,内存缓存 + 提前 5 分钟刷新;遇 401/`99991663` 立即强制刷新一次再重试。
- **写入**:`POST /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records/batch_create`(分批,单批 ≤ 500 行);覆盖场景按 `record_id` 走 `batch_update`,多余的旧行 `batch_delete`。
- **幂等**:元数据库唯一约束 `(member_id, date)`;命中且 `content_sha256` 相同 → `unchanged`;不同 → 覆盖并返回 `updated`。
- **先写库后写表**:提交记录先落元数据库(状态 `pending`),写表成功后更新为 `committed` 并保存 `record_ids`;写表失败保留 `failed` + 错误,支持重试。这样即使飞书抖动也不会丢提交。
- **重试**:仅对网络错误与 5xx 做指数退避(最多 3 次);`code != 0` 的业务错误不重试,直接返回 502。
- **日志**:记录 `submission_id`、`member`、`date`、条数、耗时、飞书 `log_id`;**不记录日报正文**。
- **超时**:飞书调用 10s 超时;整体请求 30s 内返回。

## 8. 客户端改动(很小)

现有引擎的 `submit()` 已经在向 `DIGEST_SUBMIT_URL` POST `{date, work_items}`(见 `daily_agent_digest.py`),因此:

1. 载荷扩展为第 4.1 节的字段(加 `generated_at` / `release_version` / `report_chars` / `coverage_note`,以及每项的 `status`、`source_task_ids`);
2. 新增请求头 `Idempotency-Key`,取值 `member:date:content_sha256`;
3. 设置项由 `DIGEST_FEISHU_WEBHOOK` 改为 `DIGEST_SUBMIT_URL` + `DIGEST_API_KEY`(或两者并存,见待确认 Q20);
4. 保存设置时调用 `GET /api/v1/me` 校验 Key,并把服务端返回的成员名回填显示;
5. 沿用 D-1 的规则:非 2xx 或响应体判定失败 → 保持 `report_status=ready` + `submit_status=failed`,绝不显示"已上报"。

## 9. 安全、隐私与运维

### 9.1 传输与凭据
- 只允许 HTTPS;HTTP 直接拒绝(避免 Key 明文过网)。
- Feishu App Secret 只在服务端环境变量;不进日志、不进仓库。
- 元数据库中的 Key 只存哈希;`admin` 接口单独鉴权或仅本机可访问。

### 9.2 数据与隐私
- 日报正文会经服务端中转并长期保存在飞书表格里——**这是与现状最大的差别**(现状是内容不出本机,只发一条群消息)。团队需要明确这一披露(需求 FR-14.4)。
- 后端不持久化正文(只存"是否提交过"的元数据与 record_id),正文只存在飞书表格里。
- 提供数据保留策略:例如按季度归档/清理旧表。

### 9.3 防滥用
- 每 Key 限流(建议 10 次/分钟),按 `member_id + date` 幂等。
- 可选:提交日期窗口校验(只允许当天 ±1 天),防止补交历史数据污染看板。
- 可选:日期锁定(某天已提交后只允许覆盖一次,或需要管理员解锁)。

## 10. 测试与验收

- **契约测试**:用假的飞书接口(本地 mock)覆盖 201/updated/unchanged/401/422/429/502 全部分支。
- **幂等测试**:同一 Key 同日同内容提交两次 → 第二次 `unchanged` 且不新建行;内容变化 → `updated` 且行数不变。
- **失败语义测试**:飞书返回 `code != 0` 时,客户端 `report_status` 不得为 `submitted`。
- **端到端**:对一张沙箱多维表格真写一次,人工确认字段映射与仪表盘可用。
