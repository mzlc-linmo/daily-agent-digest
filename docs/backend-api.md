# 员工日报上报 · 后端接口契约

> **这份文档的定位:只描述客户端(本仓库)已经实现、并且一定会发出去的请求,以及它对响应的要求。**
>
> 后端用什么技术栈、部署在哪、数据存哪、要不要用 Cloudflare / 自建服务 / 别的 BaaS,全部由后端自行决定 ——
> 本文不作任何技术假设。客户端只要求两件事对得上:
>
> 1. **员工持有后端签发的 API Key**(身份完全由 Key 决定,见 §2);
> 2. **请求体与响应体符合 §3 / §4 的格式**。
>
> 客户端代码里的对应实现:`daily_agent_digest.py` 的 `submit()` 与 `check_submit()`。
> 托盘界面上的两个入口:「测试连接」→ §3,「上传」→ §4。

---

## 0. 一页速览

| 事项 | 约定 |
| --- | --- |
| 员工身份 | 由 API Key 决定。客户端**不发送**姓名、工号、邮箱 |
| 客户端配置项 | 只有两个:提交地址(基地址)+ 提交 API Key |
| 校验 Key | `GET {基地址}/api/v1/me`,返回成员名用于界面回显 |
| 上报日报 | `POST {基地址}/api/v1/digests`,请求体见 §4.2 |
| 覆盖语义 | 同一「成员 + 日期」**覆盖**,不是追加 |
| 幂等 | 内容未变化时,后端应返回 `unchanged` 并且不产生重复记录 |
| 客户端超时 | `GET /me` 20 秒,`POST /digests` 60 秒 |
| 失败处理 | 非 2xx 或响应体不符合 §4.4 → 客户端标记为「未提交」并保留可重试,绝不显示为已上报 |

## 1. 角色与范围

| | 谁做 | 内容 |
| --- | --- | --- |
| 客户端(本仓库) | 已实现 | 采集本机各 AI Agent 会话 → 一次 LLM 主题归并 → 员工本地复核/排除 → 生成「按工作主题」的结构化日报 → 按天上报 |
| 后端(你) | **本次要开发** | 鉴权、API Key 的签发与撤销、按「成员 + 日期」持久化日报、以及你认可的查询/导出能力 |
| 明确不属于后端 | — | 调用 LLM、访问员工本机、采集会话日志、生成日报内容。后端只接收已经定稿的结构化结果 |

客户端保证:**只有成功做过主题归并的日报才会被上报**。未归并(LLM 未配置/失败)时客户端直接拒绝上传,
并在界面上显示原因 —— 所以后端不会收到「按来源分组的占位内容」。

## 2. API Key(必须提供)

### 2.1 为什么身份必须由 Key 承载

客户端**只**发送 API Key,不发送任何身份字段(姓名/工号/邮箱都没有)。
因此:**Key 必须在签发时绑定到具体的人**,后端从 Key 反查成员,是唯一可靠的身份来源。

### 2.2 员工如何拿到 Key(形式由后端决定,但最低要求如下)

自助申请+审批、管理员统一发放、IM 机器人自助领取……都可以。无论哪种形式,都要满足:

| # | 要求 | 原因 |
| --- | --- | --- |
| 1 | Key 与「人」绑定 | 客户端不带身份信息 |
| 2 | 一人一把(或明确的多 Key 策略并在文档写清) | 「谁提交的」必须唯一可判 |
| 3 | 明文**只在签发时展示一次**,服务端只存哈希 | 泄露面最小;客户端也只在设置里回显本机保存的值 |
| 4 | 可撤销、可轮换,**撤销立即生效** | 员工离职/换机/泄露时的止损手段 |
| 5 | 可审计:签发、撤销、每次上报都能定位到人 | 排障与合规 |
| 6 | 形态:不透明字符串,无空格/换行 | 员工要把它粘进客户端单行输入框 |
| 7 | 建议:≥32 字符随机串,可带可识别前缀(如 `dag_`) | 便于人工辨认与日志检索 |

> 客户端把 Key 存在本机 `~/Library/Application Support/Daily Agent Digest/.env`(权限 `0600`),
> 只用于发请求;它不会把 Key 写进任何日志、状态文件或上报内容。

### 2.3 员工怎么配置

托盘菜单「设置」里两项,一一对应后端的地址与 Key:

| 界面字段 | 写入 `.env` 的键 | 说明 |
| --- | --- | --- |
| 提交地址 | `DIGEST_SUBMIT_URL` | **基地址**,例如 `https://digest.example.com`。客户端自己拼 `/api/v1/me` 与 `/api/v1/digests` |
| 提交 API Key | `DIGEST_API_KEY` | 后端签发的 Key 原文 |

保存后点「测试连接」即调用 §3;不填地址或 Key 时客户端不会上报(状态显示「未配置」)。

**传输安全**:客户端会用系统 TLS 校验正常发起 HTTPS 请求。请把服务部署在 **HTTPS** 上 ——
客户端允许配置 `http://`,但 Key 会以明文经网络传输,生产环境必须是 HTTPS。

## 3. 接口一:校验 Key 并回显成员

```
GET {基地址}/api/v1/me
Authorization: Bearer <API Key>
User-Agent: DailyAgentDigest/<客户端版本>
```

**用途**:设置面板的「测试连接」。员工靠它确认「地址对了、Key 有效、而且认到的是我」。

**成功响应(HTTP 200,JSON 对象)**:

```json
{
  "member": "张三",
  "member_id": "T001",
  "key_id": "optional-key-identifier"
}
```

| 字段 | 必填 | 含义 | 客户端用途 |
| --- | --- | --- | --- |
| `member` | 是 | 成员显示名 | 界面回显:「连接成功:服务端识别为「张三」」 |
| `member_id` | 建议 | 稳定的人员标识(工号等) | 供排查;客户端不外显 |
| `key_id` | 可选 | 该 Key 的编号 | 供排查 |

**失败响应**:任意非 2xx 即可。客户端会把响应体前 200 字符显示出来。
若响应体形如 `{"error":{"code":"..."}}`,客户端会把下面两个 code 翻成可操作的提示,建议后端采用:

| `error.code` | 客户端提示 |
| --- | --- |
| `invalid_key` | 「该 Key 不存在或格式不对。请检查是否复制完整,或重新签发。」 |
| `key_revoked` | 「该 Key 已被撤销…… 请重新签发并把新 Key 填到上面的输入框。」 |

其他 code 会原样显示 HTTP 状态码与响应片段。

**超时**:20 秒。

## 4. 接口二:上报当日日报

```
POST {基地址}/api/v1/digests
Authorization: Bearer <API Key>
Content-Type: application/json
User-Agent: DailyAgentDigest/<客户端版本>
Idempotency-Key: <date>:<内容指纹 sha256>
```

### 4.1 请求体示例

```json
{
  "date": "2026-09-14",
  "generated_at": "2026-09-14T18:56:31.755811+08:00",
  "release_version": "v0.6.7",
  "report_chars": 680,
  "coverage_note": "当天入库 47 条(提示词 21 / 最终文本 26);送模型 47 条 / 18642 字符(上限 90000)",
  "work_items": [
    {
      "title": "修复日报提交的重复写入",
      "desc": "把提交改为按天覆盖,重新生成不再产生重复行,并在状态里记录 submit_mode 便于排查。",
      "status": "completed",
      "source_task_ids": ["codex/session-abc", "deepseek-harness/proj-x"]
    },
    {
      "title": "梳理托盘菜单快捷键",
      "desc": "补齐编辑菜单后 ⌘V 可用……",
      "status": "in_progress",
      "source_task_ids": []
    }
  ]
}
```

### 4.2 字段说明

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `date` | string | 是 | `YYYY-MM-DD`。**客户端本地时区固定 UTC+8**,请把它当作字符串主键,不要按服务器时区重新解释 |
| `generated_at` | string \| null | 是(可为 null) | 客户端生成报告的 ISO8601 时间,带 `+08:00` 偏移 |
| `release_version` | string | 是 | 客户端版本号(如 `v0.6.7`),便于排查某一版客户端的问题 |
| `report_chars` | number | 是 | 计入上报的正文字数(所有 `title`+`desc`),上限 1000;后端不必校验,只作统计 |
| `coverage_note` | string | 是(可为空串) | 采集与选材的一句话说明(当天入库多少条、送模型多少条),后端可原样存储备用 |
| `work_items` | array | 是 | 已排除的条目**不会**出现在这里。**数组允许为空**:员工把当天所有条目都排除时,客户端仍会照常发起一次提交(表示"当天没有计入的内容"),后端请接受空数组,或明确返回 4xx |
| `work_items[].title` | string | 是 | 工作主题,≤30 字,不含会话 ID |
| `work_items[].desc` | string | 是 | 该项的完整说明,目标 100–300 字;项多时会被压缩,但不会删条目 |
| `work_items[].status` | string | 是 | `completed` / `in_progress` / `blocked` / `observed` 之一(模型可能给出别的值,建议后端按字符串存,不要用枚举强校验) |
| `work_items[].source_task_ids` | array<string> | 是(可为空数组) | 形如 `provider/session` 的追溯标识。**后端不需要理解其结构**,原样保存即可,用于"这条日报从哪些会话来" |

规模:客户端把 `work_items` 数量约束在 0–20 条(见上),单次请求体通常 < 10 KB。
建议后端把上限放宽(例如 50 条 / 1 MB)并在超限时返回 4xx,而不是截断后静默存下。

### 4.3 语义要求(重要)

1. **按「成员 + 日期」覆盖**:同一个人同一天再次提交,应更新既有记录,**不得追加成两行**。
   客户端会在同一天多次提交(见 §5),最后一次为准。
2. **同内容幂等**:请求体内容与上次完全相同时,返回 `unchanged` 并且不产生重复记录。
   `Idempotency-Key` 头部由客户端生成(`<date>:<内容指纹>`,内容变则值变),可用于去重,也可忽略。
3. **不要合并不同成员/不同日期**;成员取自 Key,日期取自 `date` 字段。
4. 若后端希望保留历史版本(审计需要),请自己额外存版本表,但对外语义仍是"一天一条最新"。

### 4.4 响应(客户端严格要求)

成功时返回 **2xx + JSON 对象**,其中:

| 字段 | 必填 | 取值 | 说明 |
| --- | --- | --- | --- |
| `mode` | **是** | `created` / `updated` / `unchanged` | 客户端用它显示「已上传(created):3 项」;取值不在三者之内 → 客户端判定失败 |
| `submitted_at` | 否 | ISO8601 字符串 | 服务端记录的时间;缺省时客户端用本机时间填充 |

最小可用响应:

```json
{ "mode": "created" }
```

**客户端对这些情况的处理**(请后端配合,否则会显示成"未上传"):

| 后端行为 | 客户端结果 |
| --- | --- |
| 2xx + `{"mode":"updated"}` | ✅ 状态置为已上报,记住 `submit_mode` |
| 2xx 但响应体不是 JSON 对象(如数组/字符串/纯文本) | ❌ 记为失败:「提交服务返回的不是 JSON 对象」 |
| 2xx 但缺少 `mode`,或 `mode` 不是上述三值 | ❌ 记为失败:「提交服务返回了无法识别的结果」 |
| 4xx / 5xx | ❌ 记为失败,保存响应体前 300 字符;**不**标记为已上报,员工可重试 |
| 超时(>60 秒) | ❌ 记为失败,员工可重试 |

**超时**:60 秒(后端应在该时间内返回,长时间处理请改为异步并在响应里体现)。

## 5. 客户端会在什么时候发请求(后端据此设计幂等)

| 触发 | 说明 |
| --- | --- |
| 每天 18:00 后自动一次 | 前提:当天报告已生成(状态 `ready`)且已配置地址与 Key;一天只自动提交一次 |
| 员工点「上传」 | 随时可手动重提 |
| 员工在报告窗口排除/恢复条目后 | 客户端把报告标记为「内容已变」,下一轮自动重新提交 ⇒ **后端必须支持覆盖更新** |
| 未归并 / 未配置地址或 Key | **不发请求**。分别显示「日报未完成主题归并,拒绝上报」与「未配置提交地址或 API Key」 |

结论:同一个人同一天可能收到 **多次** 提交(通常 1–3 次),内容可能不同。后端请以最后一次为准。

## 6. 建议(非强制,但强烈建议)

1. **审计**:记录每次提交的成员、日期、`mode`、客户端版本、来源 IP、时间。
2. **速率限制**:每把 Key 每分钟/每天的请求上限,超限返回 429(客户端会显示失败并可重试)。
3. **数据保留**:明确保留期限与删除方式;`coverage_note` 与 `source_task_ids` 属于可追溯信息,可能涉及隐私,建议一并纳入保留策略。
4. **读取接口**:员工查看自己的历史日报、管理员导出团队日报 —— 客户端暂不使用,但团队会需要。
5. **失败可观测**:返回结构化 `{"error":{"code":"...","message":"..."}}`,便于客户端和你自己排障。
6. **不要信任客户端**:服务端应校验 `work_items` 非空、字段类型正确、`date` 格式合法,并对超长内容截断或拒绝。

## 7. 最小可用清单(可据此验收)

- [ ] 能签发 Key(绑定到人)、能撤销/轮换,且撤销后 `GET /api/v1/me` 返回 `key_revoked`
- [ ] `GET /api/v1/me` 返回 `member`(和 `member_id`)
- [ ] `POST /api/v1/digests` 完成:鉴权 → 校验 → 按「成员+日期」覆盖写入 → 返回 `mode`
- [ ] 同一天重复提交不产生重复记录;内容未变时返回 `unchanged`
- [ ] 用下面的 curl 自测通过

```bash
BASE=https://digest.example.com
KEY=dag_xxx

# 1) 校验 Key
curl -sS -H "Authorization: Bearer $KEY" "$BASE/api/v1/me"

# 2) 上报(第一次 → created,原样再发一次 → unchanged)
curl -sS -X POST "$BASE/api/v1/digests" \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 2026-09-14:test' \
  -d '{"date":"2026-09-14","generated_at":"2026-09-14T18:00:00+08:00","release_version":"test","report_chars":30,"coverage_note":"","work_items":[{"title":"联调测试","desc":"这是一条用于联调的日报内容。","status":"completed","source_task_ids":[]}]}'
```

服务端实现完成后,在客户端托盘「设置」里填入地址与 Key → 点「测试连接」应显示成员名 → 点「上传」应显示「已上传(created):N 项」。

## 8. 留给后端的开放问题(请自行决定并写进你的文档)

1. 存储与查询方式;是否需要跨天补交(员工当天没开机,第二天能否补报昨天的 `date`)。
2. 一人多 Key 是否允许;Key 的有效期;轮换策略(旧 Key 立即失效还是宽限一段时间)。
3. `source_task_ids` 是否需要落库并可检索(用于"这条日报来自哪些会话"的追溯)。
4. 团队维度的汇总口径(按人/按项目/按状态),以及是否需要日报的浏览界面。
5. 数据保留期、导出与删除流程、隐私合规(内容含工作描述,可能涉及业务信息)。
6. 申请入口的形态(自助页 / IM 机器人 / 管理员发放),以及审批与离职回收流程。

## 附录 · 客户端不会做的事(避免联调误解)

- 不会把 Key 放进 URL、日志或上报内容;
- 不会上报被员工排除的条目;
- 不会上报未完成主题归并的报告;
- 不会在未配置地址/Key、或报告不为 `ready` 时发起任何请求;
- 不会重试到无限:失败只记录状态,由下一次自动/手动提交重试。
