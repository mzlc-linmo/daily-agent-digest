# 员工日报上报 · 服务端接口契约（工作日志管理模块）

> **这份文档描述客户端(本仓库)实际发出的请求,以及它对响应的要求。**
>
> 服务端是 **linmo-pig-full 的「企业管理 → 工作日志管理」模块**
> (`EntWorkLogController`),不是本仓库的一部分。两边唯一要对齐的是:
>
> 1. **员工持有服务端签发的 API 密钥**(身份完全由密钥决定,见 §2);
> 2. **请求地址、请求体与响应体符合 §3 / §4 的格式**。
>
> 客户端代码里的对应实现:`daily_agent_digest.py` 的 `post_report()`、`submit()` 与
> `check_submit()`。托盘界面上的两个入口:「测试连接」→ §5,「上传」→ §4。

---

## 0. 一页速览

| 事项 | 约定 |
| --- | --- |
| 客户端配置项 | 只有两个:**提交地址**(基地址或完整接口地址)+ **提交 API Key** |
| 上报 | `POST {提交地址}/admin/enterprise/worklog/api/report`(地址已含该路径时不再重复拼),请求体见 §4.1 |
| 鉴权 | `X-API-Key: <密钥>`(推荐);`Authorization: Bearer <密钥>` 同样支持 |
| 员工身份 | **由密钥决定**。客户端不发送姓名、工号、邮箱,报文里没有 `username` 字段 |
| 归属日期 | **由服务端当天决定**。客户端发的 `date` 只作留痕,不参与归属 |
| 覆盖语义 | 同一「使用人 + 服务端日期」**覆盖**,不是追加;一天永远只有一条 |
| 幂等 | 报文与上次完全一致时服务端回 `unchanged`,不产生写入 |
| 客户端超时 | 60 秒 |
| 失败处理 | 非 2xx、`code != 0`、或 `data.result` 不在三态之内 → 客户端标记「未提交」并保留可重试,**绝不**显示为已上报 |
| 测试连接 | 没有独立的校验接口:客户端**用上报接口真发一次**来验证(§5) |

## 1. 角色与范围

| | 谁做 | 内容 |
| --- | --- | --- |
| 客户端(本仓库) | 已实现 | 采集本机各 AI Agent 会话 → 一次 LLM 主题归并 → 员工本地复核/排除 → 生成「按工作主题」的结构化日报 → 按天上报 |
| 服务端(工作日志管理模块) | 已实现 | 鉴权、API 密钥的签发与管理、按「使用人 + 日期」覆盖持久化日报、列表查询与导出 |
| 明确不属于服务端 | — | 调用 LLM、访问员工本机、采集会话日志、生成日报内容。服务端只接收已经定稿的结构化结果 |

客户端保证:**只有成功做过主题归并的日报才会被上报**。未归并(LLM 未配置/失败)时客户端直接拒绝上传,
并在界面上显示原因 —— 所以服务端不会收到「按来源分组的占位内容」。

## 2. API Key

### 2.1 为什么身份必须由 Key 承载

客户端**只**发送 API Key,不发送任何身份字段(姓名/工号/邮箱都没有),报文里也没有 `username`。
服务端从 Key 反查使用人,是唯一可靠的身份来源:

- 上报记录里的「使用人」= 密钥在「API密钥管理」里登记的 `使用人`;
- 密钥里存的是 `sys_user.username`,服务端每次上报还会回查用户表确认账号仍然有效;
- 因此**每个员工必须有自己的密钥**,否则所有人的日报都会记在同一个人名下。

### 2.2 密钥的创建要求

在 `权限管理 → API密钥管理 → 新增` 里创建,三个字段必须注意:

| 字段 | 必须是什么 | 填错的后果 |
| --- | --- | --- |
| 应用编码 | 必须是 `work-log` | `403 API 密钥的应用编码应为 work-log，当前为 xxx` |
| 使用人 | 必须是系统用户列表里的真实账号 | `400 API 密钥归属的使用人 xxx 不是有效用户账号` |
| 授权URL | **留空,或包含上报接口地址** | 填了别的地址 → 上报返回 `403 该 API 密钥未授权访问本接口` |

> **授权URL 是最容易踩的坑**:一旦配置,密钥就**只能**访问登记的地址,别的路径一律 403 ——
> 包括本系统里的其它接口。所以它要么留空(不限制),要么精确包含
> `{基地址}/admin/enterprise/worklog/api/report`。多个地址用逗号或换行分隔。
>
> 也正因为它只放行登记的地址,**服务端没有、也不适合有独立的「校验密钥」接口** ——
> 客户端「测试连接」因此改用上报接口本身来验证,见 §5。

明文密钥**只在创建时展示一次**(`sk-` 开头),服务端只存哈希。之后要看明文需要 `sys_apikey_secret` 权限。

### 2.3 员工怎么配置

托盘菜单「设置」里两项,一一对应服务端的地址与密钥:

| 界面字段 | 写入 `.env` 的键 | 说明 |
| --- | --- | --- |
| 提交地址 | `DIGEST_SUBMIT_URL` | **基地址或完整接口地址都行**,见下 |
| 提交 API Key | `DIGEST_API_KEY` | 服务端签发的密钥原文 |

保存后点「测试连接」即调用 §5;不填地址或 Key 时客户端不会上报(状态显示「未配置」)。

**提交地址两种写法都接受**,因为密钥的「授权URL」通常就是按完整接口地址登记的,
从「API密钥管理」页面复制过来自然带着路径:

| 写法 | 例子 | 客户端怎么用 |
| --- | --- | --- |
| 基地址 | `http://<host>/api` | 自己补上 `/admin/enterprise/worklog/api/report` |
| 完整接口地址 | `http://<host>/api/admin/enterprise/worklog/api/report` | 原样使用,不会再拼一遍 |

> 客户端按「地址是否已经以 `/admin/enterprise/worklog/api/report` 结尾」判断是哪种写法,
> 末尾多余的 `/` 会被忽略。拼错的后果很隐蔽:完整地址被当成基地址再拼一遍会变成
> `.../report/admin/.../report`,服务端只回 403「该 API 密钥未授权访问本接口」,
> 看着像密钥问题。为此客户端会把**实际请求的地址**附在失败信息里。

同一个服务的两个入口都能用,但**不要混**:

| 入口 | 该填什么 | 说明 |
| --- | --- | --- |
| 经 nginx(推荐) | `http://<host>/api` | 前端同源入口,80 端口;nginx 把 `/api/admin/**` 重写为后端 `/admin/**` |
| 直连单体服务 | `http://<host>:9999` | 绕过 nginx,调试用 |

**传输安全**:客户端会正常发起 HTTPS 请求,也允许配置 `http://`。生产环境请用 HTTPS ——
否则密钥会以明文经网络传输。

## 3. 客户端发出的请求

```
POST {基地址}/admin/enterprise/worklog/api/report
X-API-Key: <API Key>
Content-Type: application/json
User-Agent: DailyAgentDigest/<客户端版本>
```

客户端**同时也会**保留 `Authorization: Bearer` 作为兼容写法,但默认发 `X-API-Key`:

> `Authorization: Bearer sk-xxx` 会被服务端当成该密钥归属人的**完整登录态**,
> 因此还会经过全局的授权URL 拦截器。`X-API-Key` 是上报接口自己的请求头,路径更短、更不容易被误拦。

同一个地址靠 `Content-Type` 分流:`application/json` 走日报分支,表单参数走纯文本上报分支
(`title` / `content`)。本客户端只用 JSON 分支。

## 4. 上报当日日报

### 4.1 请求体示例

```json
{
  "date": "2026-09-14",
  "generated_at": "2026-09-14T18:56:31.755811+08:00",
  "release_version": "v0.6.7",
  "report_chars": 680,
  "coverage_note": "当天入库 47 条(提示词 21 / 最终文本 26);送模型 47 条 / 18642 字符(上限 90000)",
  "work_items": [
    {
      "title": "修复日报提交的重复写入",
      "desc": "把提交改为按天覆盖,重新生成不再产生重复行,并在状态里记录 submit_mode 便于排查。",
      "status": "completed",
      "source_task_ids": ["codex/session-abc", "deepseek-harness/proj-x"]
    },
    {
      "title": "梳理托盘菜单快捷键",
      "desc": "补齐编辑菜单后 ⌘V 可用……",
      "status": "in_progress",
      "source_task_ids": []
    }
  ]
}
```

### 4.2 字段说明

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `date` | string \| null | 否 | `YYYY-MM-DD`。**只作留痕**:服务端按自己的当天决定归属日,补传历史也不会散成多天。填了就必须格式合法 |
| `generated_at` | string \| null | 否 | 客户端生成报告的 ISO8601 时间,带 `+08:00` 偏移。服务端取**墙上时间**原样留痕,不参与入库时间 |
| `release_version` | string | **是** | 客户端版本号,≤64 字。空 → 400 |
| `report_chars` | number | **是** | 计入上报的正文字数(所有 `title`+`desc`),服务端只作统计。为 null → 400 |
| `coverage_note` | string | 否 | 采集与选材的一句话说明,≤1024 字 |
| `work_items` | array | **是** | **允许空数组**(表示当天没有计入的内容),但**不能为 null** |
| `work_items[].title` | string | **是** | 工作主题,≤30 字,不含会话 ID。空 → 400 |
| `work_items[].desc` | string | **是** | 该项的完整说明,目标 100–300 字。空 → 400 |
| `work_items[].status` | string | **是** | `completed` / `in_progress` / `blocked` / `observed`。服务端**按字符串存**,不做枚举强校验 |
| `work_items[].source_task_ids` | array\<string\> | 否 | 形如 `provider/session` 的追溯标识。服务端不解释结构,原样保存 |

规模:客户端把 `work_items` 约束在 0–20 条,单次请求体通常 < 10 KB。

### 4.3 规模与校验上限(超限返回 4xx,**不截断**)

| 项 | 客户端约束 | 服务端上限 | 超限响应 |
| --- | --- | --- | --- |
| `work_items` 条数 | 0–20 | 50 | `400 work_items 条目超限（最大 50，当前 N）` |
| 请求体大小 | 通常 < 10 KB | 1 MB | `413 请求体超限（最大 1MB，当前 N 字节）` |
| `release_version` | 版本号 | 64 | `400 release_version 超长` |
| `coverage_note` | 一句话 | 1024 | `400 coverage_note 超长` |
| `title` | 30 | 200 | `400 work_items[i].title 超长` |
| `desc` | 100–300 | 20000 | `400 work_items[i].desc 超长` |
| `status` | 四态之一 | 32 | `400 work_items[i].status 超长` |
| `source_task_ids[]` | 追溯标识 | 200 | `400 work_items[i].source_task_ids 单项超长` |

### 4.4 语义要求(重要)

1. **使用人取自密钥**:报文里带 `username` 也不会被采纳(JSON 分支根本没有这个字段)。
2. **归属日由服务端决定**:`report_date = DATE(服务端上报时间)`,标题自动生成
   `日报 <服务端当天>`。客户端传的 `date` 只存进留痕字段。
3. **按「使用人 + 归属日」覆盖**:同一个人同一天再次提交,更新既有记录,**不得追加成两行**。
   客户端会在同一天多次提交(见 §6),最后一次为准。
4. **同内容幂等**:报文与上次完全一致时返回 `unchanged`,不产生写入(只刷新最新上报时间)。
5. **初次上报时间保持首值**,最新上报时间每次刷新。
6. 两条上报通道(JSON 日报 / 表单)共用 `(username, report_date)` 唯一键 —— 同一天只会有一行。

### 4.5 响应(客户端严格要求)

服务端返回 Pig 的 `R` 包装,业务结果在 **`data`** 里:

```json
{
  "code": 0,
  "msg": null,
  "data": {
    "result": "created",
    "id": "2100032113605980162",
    "username": "hudan",
    "date": "2026-09-16",
    "itemCount": 1,
    "written": true
  },
  "ok": true
}
```

| 字段 | 必填 | 取值 | 说明 |
| --- | --- | --- | --- |
| `code` | **是** | `0` = 成功 | 非 0 一律判为失败(即使 HTTP 是 200) |
| `data.result` | **是** | `created` / `updated` / `unchanged` | 客户端用它显示「已上传(created):3 项」;取值不在三者之内 → 客户端判定失败 |
| `data.username` | 建议 | 服务端由密钥解析出的使用人 | 供排查;客户端不外显 |
| `data.date` | 建议 | 服务端归属日 `YYYY-MM-DD` | 供排查。**可能与报文里的 `date` 不同**,这正是"归属日由服务端决定"的体现 |
| `data.itemCount` | 否 | 条目数 | 供排查 |
| `data.written` | 否 | `unchanged` 时为 `false` | 供排查 |
| `data.submitted_at` | 否 | ISO8601 字符串 | 服务端**不返回**此字段;客户端缺省时用本机时间填充 |

`result` 三态:

| 值 | 含义 |
| --- | --- |
| `created` | 该使用人该日期首次上报 |
| `updated` | 同人同日已存在且内容有变化,已覆盖(**不会追加成两行**) |
| `unchanged` | 报文与上次**完全一致**,未产生任何写入 |

**客户端对这些情况的处理**(服务端行为不对时界面会显示成"未上传"):

| 服务端行为 | 客户端结果 |
| --- | --- |
| 2xx + `code=0` + `data.result = updated` | ✅ 状态置为已上报,记住 `submit_mode` |
| 2xx 但响应体不是 JSON 对象(数组/字符串/纯文本) | ❌ 记为失败:「提交服务返回的不是 JSON 对象」 |
| 2xx 但 `code != 0` | ❌ 记为失败,并显示 `msg` |
| 2xx 但缺 `data.result`,或取值不在三态内 | ❌ 记为失败:「提交服务返回了无法识别的结果」 |
| 4xx / 5xx | ❌ 记为失败,保存 `msg`;**不**标记为已上报,员工可重试 |
| 超时(>60 秒) | ❌ 记为失败,员工可重试 |

### 4.6 失败响应

非 2xx 时同样是 `R` 包装,**原因在 `msg` 里**(注意:不是 `{"error":{"code":...}}`):

```json
{ "code": 403, "msg": "该 API 密钥未授权访问本接口（当前密钥的授权URL：...）", "data": null, "ok": false }
```

客户端会把 `HTTP <状态码>: <msg>` 原样显示在设置面板与状态文件里。

| 状态码 | `msg` | 处理 |
| --- | --- | --- |
| 401 | `缺少 API 密钥（请通过 X-API-Key 请求头携带）` | 补上请求头 / 检查设置里的 Key |
| 401 | `API 密钥无效、已禁用、已过期或来源 IP 不在白名单` | 核对密钥;检查「是否启用 / 过期时间 / IP白名单」 |
| 403 | `API 密钥的应用编码应为 work-log，当前为 xxx` | 换了别的模块的密钥,重新签发 |
| 403 | `该 API 密钥未授权访问本接口（当前密钥的授权URL：…）` | 把上报地址加进授权URL,或清空该字段 |
| 400 | `API 密钥归属的使用人 xxx 不是有效用户账号` | 密钥的使用人被删了或改了名,编辑密钥重选 |
| 400 | `work_items[i].desc 不能为空` 等 | 报文不合法,按 §4.3 修正 |
| 409 | `日报上报重复提交，请稍后重试` | 3 秒内并发重复提交被幂等插件拦下;串行重放会返回 `unchanged` |
| 413 | `请求体超限` | 精简 `work_items` |

## 5. 「测试连接」= 用上报接口试传一次

设置面板的「测试连接」**没有独立的校验接口可用**(原因见 §2.2:密钥的授权URL 只放行上报路径,
任何其它路径都会 403)。所以它改为**调上报接口真发一次**,用服务端回的 `username` 回答三个问题:
地址对不对、Key 有没有效、认到的是谁。

客户端为此把状态一并回传:`{member, date, mode, item_count}`,界面显示
「连接成功：服务端识别为「hudan」,并已试传今天的日报(created,3 项)」。

试传的内容按当天状态决定:

| 当天状态 | 试传的内容 | 原因 |
| --- | --- | --- |
| 日报已归并(`report_status=ready`) | **当天真实的日报内容** | 顺便把当天的日报送达,和点「上传」效果一致 |
| 尚未归并,且当天**没有**成功上报过 | 空 `work_items` 探针 | 服务端允许空数组;配置刚填好、还没生成日报时也能验证 |
| 尚未归并,但当天**已经**成功上报过 | **拒绝试传**并说明原因 | 空内容会把服务端已有的那份日报覆盖掉 |

> 因为同人同日是覆盖语义,「测试连接」是**真上报**:它写入/刷新当天那条记录,不会多出一行。
> 设置面板里的提示已写明这一点。测试用的是输入框里的值(不落盘),所以测试失败不会污染已保存的配置。

## 6. 客户端会在什么时候发请求(服务端据此设计幂等)

| 触发 | 说明 |
| --- | --- |
| 每天 18:00 后自动一次 | 前提:当天报告已生成(状态 `ready`)且已配置地址与 Key;一天只自动提交一次 |
| 员工点「上传」 | 随时可手动重提 |
| 员工在报告窗口排除/恢复条目后 | 客户端把报告标记为「内容已变」,下一轮自动重新提交 ⇒ **服务端必须支持覆盖更新** |
| 员工点「测试连接」 | 用上报接口试传一次(§5) |
| 未归并 / 未配置地址或 Key | **不发请求**。分别显示「日报未完成主题归并,拒绝上报」与「未配置提交地址或 API Key」 |

结论:同一个人同一天可能收到 **多次** 提交(通常 1–3 次),内容可能不同。服务端以最后一次为准。

## 7. 服务端已提供、客户端暂未使用的接口

以下接口要 JWT + 对应权限,**密钥调不通**(会被授权URL/登录态拦截),仅供管理端使用:

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| GET | `/admin/enterprise/worklog/page` | `ent_worklog_view` | 按使用人 / 日期区间 / 标题分页查询 |
| GET | `/admin/enterprise/worklog/details/{id}` | `ent_worklog_view` | 单条详情 |
| POST | `/admin/enterprise/worklog/report` | `ent_worklog_add` | 登录用户表单上报 |
| GET | `/admin/enterprise/worklog/export` | `ent_worklog_export` | 导出 Excel |
| GET | `/admin/enterprise/worklog/export-markdown` | `ent_worklog_export` | 按当前筛选导出 Markdown |
| GET | `/admin/enterprise/worklog/export-markdown/{id}` | `ent_worklog_export` | 单行导出 Markdown |
| DELETE | `/admin/enterprise/worklog` | `ent_worklog_del` | 删除 |

## 8. 自测与联调

```bash
BASE=http://192.168.110.164/api      # 基地址:nginx 入口
KEY=sk-xxxxxxxx                       # app_code = work-log 的密钥
URL="$BASE/admin/enterprise/worklog/api/report"

# 1) 上报(第一次 → created)
curl -sS -X POST "$URL" \
  -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"date":"2026-09-18","generated_at":"2026-09-14T18:00:00+08:00","release_version":"tetest",
       "report_chars":301,"coverage_note":"",
       "work_items":[{"title":"联调测试","desc":"这是一条用于联调的日报内容。","status":"completed","source_task_ids":[]}]}'

# 2) 原样再发一次 → updated(同一天内容变了)或 unchanged(内容一字不改)

# 3) 查列表确认「一天只有一条」(需要管理员 JWT)
curl -sS "$BASE/admin/enterprise/worklog/page?current=1&size=10&startDate=2026-09-16&endDate=2026-09-16" \
  -H "Authorization: Bearer $TOKEN"
```

服务端实现完成后,在客户端托盘「设置」里填入地址与 Key → 点「测试连接」应显示成员名与试传结果 →
点「上传」应显示「已上传(created):N 项」。

### 常见现象与原因

| 现象 | 原因 |
| --- | --- |
| 上报返回 `403 该 API 密钥未授权访问本接口` | 密钥配了授权URL,但不包含上报地址。**先看失败信息里的「客户端实际请求」**:地址被拼了两遍(`.../report/admin/.../report`)说明提交地址填的是完整接口地址而老客户端把它当成了基地址(当前版本已兼容两种写法) |
| 上报返回 `403 应用编码应为 work-log` | 用了别的模块的密钥 |
| 返回的 `data.date` 与报文里的 `date` 不同 | **正常**:归属日由服务端当天决定,报文的 `date` 只作留痕 |
| 「测试连接」提示已上报过、拒绝试传 | 当天日报已成功上报且当前未处于 `ready`,试传的空内容会覆盖它(§5) |
| 改动内网地址后旧记录仍在旧日期下 | 归属日取服务端当天,补传历史不会散成多天 —— 这是刻意设计 |

## 附录 · 客户端不会做的事(避免联调误解)

- 不会把 Key 放进 URL、日志或上报内容(状态文件里也没有密钥);
- 不会上报被员工排除的条目;
- 不会上报未完成主题归并的报告(「测试连接」的空探针除外,且它受 §5 的覆盖保护约束);
- 不会在未配置地址/Key、或报告不为 `ready` 时发起自动上报;
- 不会重试到无限:失败只记录状态,由下一次自动/手动提交重试。
